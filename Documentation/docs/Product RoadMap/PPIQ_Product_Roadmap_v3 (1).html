PlantProcess IQ — Product Roadmap

From laptop software → a product you sell · €35k → €60k → €120k → €250k + first contract. A product ships when all six buyer lenses can sign; the headline is the lowest, never an average. Euros = customer-side willingness-to-pay, not quotes.

The rule that fixes 6-June: every task is a binary gate with an evidence artifact — a task is done when its gate is green, not when code was written. What is not measured is not achieved. The value jumps are mostly not code: €35k→€60k = a demo that runs live; €120k→€250k = one reference customer.

v3.1 adjustment (market benchmark + pilot model): the €35k→€60k→€120k→€250k figures are market value, not the invoice. You propose a €30–40k paid pilot now (lean €30k for the first customer) crediting toward a €120k/yr license; €120k is what you convert to after proven ROI on the customer's data, and the pilot/contract runs right after the M1 presentation (M2 overlaps it, customer-funded). PPIQ is a Tier-2 specialist, read-only — lower price ceiling than prescriptive peers SST/Fero — so the path is proof + service + a reference, not more features.

The surprise-question gate — the objections the demo must survive (rehearse these)

A skeptical buyer asks these live. The five you must nail cold are below; full set in the .md.

"Briefly — what is it and why should I buy it?"
A read-only, evidence-grade layer that connects your fragmented plant data and shows suspected drivers of quality/downtime with the population and the math shown — faster than spreadsheets, without touching control systems.
"Do you send my data to GPT/Claude?"
No. Engines run in-tenant; the assistant model is self-hosted by default, or a zero-retention private endpoint receiving only the question + scoped evidence; a per-tenant no-egress toggle exists.
Evidence: PrivateModelGatewayContracts.cs:13
"Is it AI, or simple math?"
Deterministic engines compute and rank; the assistant only explains, and cannot render an uncited number.
Evidence: GroundingService.cs:42; AdvancedCorrelationComputeService.cs
"Can I change pages/widgets/jobs myself, or only in source?"
From the HMI. A script layer adjusts widget behaviour so there's no endpoint-per-widget.
Evidence: p3T15WidgetSchemaContract.ts
"How do you control the license — can I just edit my tier?"
No. Entitlements come from an Ed25519-signed token, not an editable DB row — a tamper test proves mutating the tier changes nothing.
Evidence: VerifiedEd25519LicenseService.cs; Phase5_LicenseTierTamperTests.cs:8
"GPT-3 erred often — how can I depend on your assistant?"
Because the assistant doesn't compute or rank — deterministic engines do, and every assistant claim carries a resolvable evidence handle or is not rendered.
The close, every time: "suspected contributor, not guaranteed root cause — read-only, no OT control." That honesty is the differentiator vs prescriptive tools (SST/Fero).

The stable environment — fix the root cause once (M1, Day 1)

Your failing tests, your failing demo dry-run, and your vanishing credentials are one problem: non-reproducibility. Move local-only creds into version control (they only ever point at local containers, so they're not secrets); keep real secrets in a git-ignored .env on the VPS. A clean checkout + ppiq.ps1 demo then always boots an identical seeded, credentialed, licensed system. M1-7's gate — ppiq.ps1 test exits 0 twice on a clean machine — is the permanent end of the 83-failure struggle.

One canonical compose + overlays

  • docker-compose.yml base (app DB)
  • .sources.yml — 8 emulated sources (demo)
  • local / ci / server overlays
  • delete the 3 duplicate trees

App DB = ONE database, TWO schemas

  • ppiq_meta — dashboards, widgets, jobs, pages, users, roles, license
  • ppiq_plant — customer data after staging transform (RLS)

Committed fixtures (never vanish)

  • demo/ — 630 heats / 5,600 coils
  • users/ — one user per role
  • license/ — dev Ed25519 keypair + per-tier tokens

One entrypoint ppiq.ps1

  • up · migrate · seed · test · e2e · demo · reset · down
  • loads .env.dev — no hand-set vars ever

Auth, ready for test/e2e/run

  • License: committed dev keypair; prod uses SOU's real key
  • Users: seeded per role, known dev passwords

Why it's the right pattern

  • identical local/CI/server topology
  • zero manual setup; one-command clean rebuild
  • "deploy to server & customer" falls out
