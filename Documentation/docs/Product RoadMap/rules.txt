## 0 · How to use this document

Three layers, applied in order:

- **Part A — Six evaluation personas.** PPIQ is judged from six independent professional vantage points, each scoring **8–12 criteria**. Every criterion states *what must be true*, *the hard test that proves it*, and *the failure condition that fails it*.
- **Part B — Capability & domain specification.** The objective backbone the personas score against: every feature, workflow, job, the generic-platform mandate, and the complete flat-steel demo blueprint (equipment, every source database and its tables, the downtime model, the dataset scale). This is the ground truth; if a persona criterion and Part B disagree, Part B wins.
- **Part C — Scoring doctrine & the surprise-question gate.** The bands, the evidence rule, the persona-and-gate reconciliation, and the live buyer-objection playbooks the demo must survive.

**Four standing rules bind the entire review (expanded in C4):**
1. **No score without a live demonstration** through the HMI on the demo dataset.
2. **Honesty outranks capability** — a confident wrong answer scores *below* an honest "collecting data," and any forbidden commercial claim is automatically Critical.
3. **The demo path is sacred** — every button on it works, or the path is not demo-ready (the no-"85%" rule).
4. **Read-only and OT-safety are absolute** — any write-back path to a control system is an automatic Critical, regardless of all other strengths.

A build that satisfies one reviewer and fails another is **not shippable**. The headline result is the **lowest** persona score, never an average that hides a failing dimension.

## A1 · The Developer / Maintainer

*"Can I extend this codebase a year from now without it fighting me — and is it honest about what it actually does?"*

| # | Criterion | Hard test (how the reviewer proves it) | Failure condition |
|---|-----------|----------------------------------------|-------------------|
| 1 | **Code hygiene & clean code** | Static scan + manual read of 10 random files: no commented-out code blocks, no `*.runtime.cs`/shim tombstones, no duplicated logic that should have one home, consistent formatting (UTF-8, LF). | Any tombstone shim, any duplicated decision (e.g. the same provider-availability array in 3 places), any dead code. |
| 2 | **Stability under change** | `dotnet test Backend` + `vitest` + `e2e` all run green twice consecutively; no flaky test; no environment-specific config required to build. | Any flaky test; any "works on my machine" config; a green deploy sitting on a red suite. |
| 3 | **Repo cleanliness & structure** | Confirm one canonical layout (`Domain / Application / Analytics.Core / Analytics.Engine / Infrastructure / Workers / Api`); grep for duplicate Jenkinsfiles, stray `docker-compose.yml`, committed backup folders, unregistered test projects. | Any duplicate pipeline/compose file, any orphaned backup folder, any test project missing from the solution. |
| 4 | **Representative naming & file structure** | Open any unfamiliar class; its name predicts its content; partial files follow one naming convention; one tier enum, not three. | A file whose name misrepresents content; >1 license-tier enum; inconsistent partial-file naming. |
| 5 | **Test architecture — execution, not enumeration** | Inspect the Jenkinsfile and the test projects: `dotnet test`, `npm run test`, and `npm run e2e` are invoked as **blocking** stages that **execute** (no `--list`, no `catchError(SUCCESS)`); skips are registered in a `TESTS.md`-style ledger with justification. | Tests enumerated not run; failures swallowed; an unregistered skip; e2e wrapped to always pass. |
| 6 | **Generic — any plant, any DB, any domain** | With no code change, link each of the six source types (MSSQL, PostgreSQL, MySQL, Oracle, Excel, CSV); confirm no plant name, product, routing, schema, or defect type is hardcoded anywhere. | Any hardcoded plant/product/schema/route; a connection target compiled into the binary; a defect type baked into code. |

Prove the red path: break one test, push, confirm the deploy stages never run; revert, confirm green deploys. *(As of 26 Jun 2026 this pipeline is GREEN end-to-end on the server, build #96; the app-project rename `plantprocessiq`→`ppiq-app` is what stopped `--remove-orphans` from reaping Jenkins.)* | Any extra pipeline step beyond the agreed sequence; the app deploy sharing a project name with infra so `--remove-orphans` reaps Jenkins/Caddy; any orphaned/parallel app stack; a deploy reachable while a suite is red; wrong connection-string key (`DefaultConnection` instead of `PlantProcessDb`) or missing signing key. |
| 10 | **Switchable run/test profiles (local & server)** | Demonstrate exercising **every** auth/license combination locally and on the server **without code edits or DB surgery**: seeded one-user-per-role and a forced-tier switch, applied via config/overlay, **refused in Production** unless an explicit accept-risk flag is set. Confirm the reviewer can log in as Admin / Executive / Engineer / Operator and force Light→Enterprise on demand. **Both environments must be honoured as first-class:** LOCAL uses the five dev-seed config users (`deploy/compose/.env.dev`) for daily development/testing; SERVER login is DB-backed (`app_users`) with the permanent `sysadmin` (auto-provisioned, support-only) and the customer admin added manually at commissioning — never a customer-named admin baked into the install image. | Testing different auth/license states requires editing code or hand-editing the DB; a test-mode switch silently active in Production; a customer-usable admin shipped in the install image; the demo dev license key registered in a real customer Production. |
| 11 | **No silent failure anywhere** | Force one widget's data endpoint to 500: confirm a **contained, branded, retryable** error in that widget while the rest of the page stays interactive; confirm **zero** unhandled promise rejections in the console across the demo path. | Any "could not load … works on retry"; a single widget error blanking a page; an unhandled rejection in the console. |

## A2 · The Security & IT / Procurement Reviewer

*"Can my automation team and my DBA approve this without a control-systems risk review or a data-egress concern?"*

The veto-holder in any real plant sale. This is the entire content of Doctrine Wave A and §18.

| # | Criterion | Hard test | Failure condition |
|---|-----------|-----------|-------------------|
| 1 | **Read-only is absolute** | Code-search every source/control path for any write/setpoint/command/DDL-on-source; confirm outbound is only message/export/webhook. | Any write-back path of any kind to a source or control system. |
| 2 | **OT-safe acquisition topology** | Confirm sources are reached through a customer-controlled Edge Collector that **pushes one-way**; the core never initiates a connection into OT; a data-diode option is documented. | The core connects *into* the OT network; any inbound path to control; no collector model. |
| 3 | **Source-load protection** | Confirm per-source row caps, statement timeouts, rate limits, approved windows; backfill is throttled, resumable, checkpointed — never one giant query against the primary. | An unbounded query against a production source; a backfill that is one giant SELECT. |
| 4 | **Token & session security** | Confirm the access token lives **in memory + an HttpOnly refresh cookie with rotation/revocation** — *not* localStorage; Argon2id password hashing; MFA enforced for admins. | A token in browser localStorage; a hardcoded/weak hash; no admin MFA path. |
| 5 | **Secrets handling** | Confirm source credentials live only in the collector's encrypted vault, masked on read-back, never in the browser or app config; per-environment signed keys, no hardcoded signing key. | Any credential in browser/config; a hardcoded JWT signing key; an unmasked secret on read-back. |
| 6 | **Tenant isolation** | Confirm SaaS = TenantId + row-level security and dedicated = physical isolation, one resolver/one ruleset; run a cross-tenant request and confirm **403/empty**. | Cross-tenant data leakage; separate code forks per topology. |
| 7 | **Per-endpoint authorization** | Enumerate endpoints/pages/jobs/tools via `EndpointDataSource`; confirm each checks role + entitlement; confirm **no** dev-seed or diagnostic/proof endpoint is reachable in a production build. | Any unguarded admin surface; any dev-seed/diagnostic endpoint exposed in prod. |
| 8 | **AI data boundary** | Confirm engines compute in-tenant; the assistant model is self-hosted by default, or a zero-retention private endpoint receiving **only** the question + scoped evidence; a per-tenant no-egress toggle exists. | Plant data sent to an external model for computation; no no-egress toggle; the assistant doing arithmetic. |
| 9 | **Audit & encryption at rest** | Confirm an append-only, immutable audit log on sensitive actions and encryption at rest. | Mutable/absent audit log; plaintext at rest. |
| 10 | **Deployment hardening** | Confirm the database port is bound to 127.0.0.1 (not publicly exposed), the bootstrap admin is replaced, health/readiness endpoints exist, and runbooks exist. *(As of 26 Jun 2026 the bootstrap admin is replaced by the permanent `sysadmin` owner auto-provisioned at first run — a support-only account the customer never uses; health endpoints are anonymous and the deploy is health-gated with rollback to `:previous`. Still verify the server DB-port binding.)* | A publicly exposed DB port; an active bootstrap admin; a customer-usable admin shipped in the image; no health/readiness; no runbook. |

**Why this persona cannot be gamed:** every prior-audit finding (localStorage token, hardcoded JWT key, unconditional dev-seed, exposed PostgreSQL port, bootstrap admin) is an explicit, individually testable failure condition. Each is binary.

# PART B — Capability & Domain Specification (the objective backbone)

The personas score against this. It is organized on the V1 four-track skeleton the doctrine preserves.

## B0 · The product in one line

PPIQ is a **generic, read-only, evidence-grade plant-intelligence platform**: each plant connects its own sources, defines its own mappings, builds its own pages, monitors its own jobs, and investigates its own quality / downtime / KPI questions — carried from fragmented raw data to trustworthy understanding, **never asked to take a black box on faith**.

## B0.1 · The generic mandate (why nothing may be hardcoded)

The product installs in **any** plant, and every plant differs in: database **types**; database **structures and tables**; **inspection devices** that generate different defect types and structures; **production-line** structures; **processes and unique workflows**; and the **focus of each CEO and process engineer** — different parameters, KPIs, and correlations. Therefore the data domain model, every endpoint, and every surface must be generic, achieved by: (a) connecting to all six source types; (b) admin-defined DB links with per-table import selection and per-object sync cadence; (c) admin-authored mapping/views into one generic schema; and (d) HMI-built pages/widgets with a script layer — so the same binary serves every plant by **configuration, not code**.

---

## Track 1 — Workflow & Product

### B1.1 · Generic source integration (Admin → DB-Configuration → DB-Link tab)
**Must do:** connect MSSQL / PostgreSQL / MySQL / Oracle / Excel / CSV with no code change.
**How:** admin links a source, picks a provider, the system **tests connectivity before save**, masks credentials, the admin selects which tables to import and sets the read/import cadence (every **2 min up to several days**); the connector catalog declares **honest availability per source version**.
**Evidence to find:** all eight demo sources linkable through the HMI; a not-yet-certified connector says so rather than claiming "live Oracle ready today."
**Gate G1 · Track 1.**

### B1.2 · The staging / dump layer
**Must do:** hold the **latest source-shaped copy** of each customer object — *not* PPIQ's structure.
**How:** namespaced tenant/source staging; on each scan the system compares the **last index in the dump** against the **source table's last index** and imports only the new records; every sync writes an import batch (rows, duration, watermark, errors). Each import is a **named job with a cycle and a crash status**.
**Evidence to find:** a re-sync imports only the delta; staging stays source-shaped; canonical transformation happens later.
**Gate G1.**

### B1.3 · Mapping & joining engine — *the heart* (Admin → Schema-Configuration page, multiple tabs)
**Must do:** turn many foreign keys into one canonical fact, generically — the one place the compass explicitly asked for a complete, effective, advanced, professional, detailed, generic design.
**How:** a **layered join model** from business keys, strengthened through normalization, mapping views, genealogy, and a confidence score; a **business-key dictionary** reconciles mismatched IDs explicitly (HSM Oracle `pieceId` ≡ Parsytec MySQL `materialId`; "C-0044170" ≡ "44170") and **rejects conflicts rather than silently merging**; a mapping-authored **safe-SQL view** (read-only; INSERT/UPDATE/DELETE/DROP/DDL-on-source rejected; implicit row limit + statement timeout; `EXPLAIN` before publish; typed errors) produces canonical facts by walking slab → coil → defect; **KPIs are first-class versioned SQL views** (e.g. First-Pass Surface Yield by grade/day), consumed by widgets *and* the KPI-contributor learning job; a normalized EAF process model (a `processDefinition` table of process-id/name and a values-against-heat table) is joined by user or automatic script.
**Tiered authoring (the answer to "must my configurator be a programmer?" — for the common case, no):**

| Tier | Offers | Who |
|------|--------|-----|
| No-code visual mapper | drag-drop field mapping, point-and-click joins on detected keys, industry & KPI templates — the common majority, zero SQL | process / quality engineer |
| Assisted | profiling suggests keys/normalization/joins with confidence; the assistant drafts a view from a plain-language description for a human to review (execution stays deterministic) | engineer + reviewer |
| Expert SQL | the safe-SQL view builder for the complex long tail | data engineer (customer or SOU) |

**Evidence to find:** a coil resolves **both** genealogy directions on demo keys; a bad mapping returns a typed error and **rolls back**.
**Gate G2 · Track 1.**

### B1.4 · Import execution (Admin → DB-Configuration → Importing-Data tab)
**Must do:** after mapping/scripting/views/joins are configured, import from the dump files into PPIQ's generic schema on a cadence that drives HMI refresh when new data is ready.
**How:** the import is a **named job with cycle and crash status**; cadence is admin-set.
**Gate G1/G3.**

### B1.5 · Page & widget building (Front-End — config-from-HMI)
**Must do:** create/modify/delete pages and place widgets with **no** source edit.
**How — Creating Page:** a user creates/deletes/modifies any page; a **widget library** (all charts, KPIs, sorting/filtering tools — date-time, list-of-values) is drag-dropped onto the page, then **Save**; existing pages can be edited (add/delete a widget) and saved.
**How — Widget:** the selected widget has an **edit button** to bind it to a list of values from the DB; a **script layer** adjusts behavior (e.g. a bar chart "group by shift") so the product does **not** need an endpoint per widget — otherwise it would need 100k endpoints, which violates generic design.
**Evidence to find:** the **entire demo builds from empty through the HMI** — no hardcoded page or widget.
**Gate G3 · Track 1.**

### B1.6 · The engine's learning jobs (Functionality)
**Must do:** learn correlations across the plant on a schedule (typically off-hours) or on demand.
**How — four standing jobs, each monitored in the Jobs-Monitor page:**
1. parameter ↔ **all defect IDs** (e.g. daily / user-defined, off-hours, long-running);
2. parameter ↔ **downtime IDs** (same cadence);
3. parameter ↔ **all defined KPIs** (same cadence);
4. an **overall** job across all data (e.g. weekly / user-defined).
The correlation engine uses the L4 method set — **Spearman rank correlation, mutual information, Lasso, VIF (multicollinearity), and bootstrap** — under **Benjamini-Hochberg FDR control and stratification** by every visible confounder; results are framed as *suspected contributors*, never causes.
**Gate G4/G5 · Track 1.**

### B1.7 · Correlation page (ML area — one tab per generated job)
**Must do:** let a user investigate a specific outcome.
**How:** the user selects a specific **defect ID / downtime ID / KPI ID** and an inspection window (last week / month / year), names the inspection job, and runs it on the learning engine; on completion it **generates a page** of widgets/charts showing which parameters most influence the outcome; the user can **save** the page and run it **periodically** (e.g. hourly/daily) or on demand via a **Run** button.
**Gate G4 · Track 1.**

### B1.8 · Suggestion & recommendation page (ML area)
**Must do:** turn the four standing jobs' learning into plant-improvement suggestions.
**How:** a **deterministic** suggestion engine; the assistant **explains** with citations and **cannot render an uncited number** (a **no-fabrication guard** rejects any number without a resolvable **evidence handle** before display); an evaluation harness gates regressions.
**Evidence to find:** the assistant emits **no uncited number**; on a transition coil it answers with weighted shared attribution.
**Gate G4 · Track 1.**

### B1.9 · Value engine
**Must do:** convert a finding into money, honestly.
**How:** the §7.5 formula with a per-tenant cost table and an **abstain path**; downtime modeled as **two distinct quantities** — *equipment-stopped minutes* vs *production-impact minutes* — and the right one used (see the downtime model in B-demo).
**Evidence to find:** a finding reproduces a **bounded euro range** (e.g. €28k–€56k) on demo data, every input drill-throughable; the engine abstains rather than inventing a number. *(The single largest doctrine-to-build gap — score strictly.)*
**Gate G5 · Track 1.**

## Track 2 — Hardening (the go-live quality bar)

The standing instruction: **no error, bug, crash, or non-functional command is acceptable in front of the customer.** Specifically — never a "view could not load / this part of the page could not load" that then works on retry; never a styling mismatch (the Material-Investigation search/load/calculate/PDF buttons must be standard, and standard **everywhere**, current and future); never a button that doesn't perform its function (min/max, calculation, loading).

**Enumerated hardening checklist (every item is a test):**
1. **Buttons** — every button on every current and future page/tab matches the standard style **and** performs its function 100%.
2. **Tables** — all tables share one style.
3. **Tabs & wording** — consistent across all current and future pages/dashboards.
4. **Layout** — alignment, orientation, and component placement are perfect, advanced, professional from a UI/UX standpoint, everywhere.
5. **Widget interaction** — drag/drop/move/min/max done correctly.
6. **Responsiveness** — every page renders correctly at every screen size, on any browser, over http/https, and re-flows properly.

8. **Endpoint resilience** — every current and future API + its SQL/joins handles PK/FK/null without an expected failure.
9. **No surprises** — nothing breaks unexpectedly in front of the customer.
10. **Every interactive element** — every button, component, hook, and recall performs its function 100% correctly.
11. **Action coverage** — every action on every page/sub-page/navigation is tested.
12. **Intelligence ready** — ML, correlation, and suggestion/recommendation are ready.
13. **Dynamic widgets** — all widgets/charts are dynamic and interactive and work with filter/sort.
14. **Heatmap** — renders and interacts correctly.
**Gate G6/G10 · Track 2.**

# PART C — Scoring Doctrine

## C1 · Per-criterion bands

Each criterion is scored **/100**:

| Band | Score | Meaning |
|------|-------|---------|
| **Critical** | < 55 | Missing, broken, or dishonest. A dead button on the demo path, a fabricated/uncited number, a forbidden commercial claim, a write-back path to control, or any live prior-audit security finding lands here **regardless of other strengths**. |
| **Needs work** | 55–69 | Present but incomplete, fragile, or inconsistent — works in the happy path, fails an edge state, a second browser, an induced fault, or a skeptical click. |
| **Solid** | 70–84 | Complete, stable, and honest for the demo scope; meets the gate's measurable exit on demo data. |
| **Strong** | 85+ | Production-grade beyond the demo: enumerated, automated-tested, documented, robust under adversarial use. |

Each scored criterion records four things — **Present** (what exists), **Why not lower** (the evidence that earns the floor), **Why not higher** (the specific named gap to the next band), and **Evidence** (file\:line or a reproducible run/command). **A criterion with no reproducible evidence cannot exceed *Needs work*.**

## C2 · Persona score & overall

A persona's score is the evidence-weighted mean of its criteria, with a **hard cap**: a **Critical** on any safety, honesty, dead-button, or read-only criterion caps the whole persona at **Needs work** until fixed. The six persona scores are reported **side by side and never averaged into one number**; the **headline is the lowest persona score**, because the build ships only when the developer, the security reviewer, the quality engineer, the operations admin, the executive, **and** the brand can each sign.

The reviewer confirms each scored point traces to a gate, a wave, and reproducible evidence.

## C4 · The reviewer's standing rules (binding)

1. **No score without a live demonstration** through the HMI on the demo dataset. A claim in a document, a comment, or a conversation is worth zero.
2. **Honesty outranks capability.** An honest "collecting data" beats a confident wrong answer; any forbidden commercial claim (Appendix-E list) is Critical even on an otherwise strong surface; any uncited number from the assistant is Critical.
3. **The demo path is sacred.** Every button on the path works, or the path is not demo-ready — the no-"85%" rule (a gate item is 95–100% or it is not done).
4. **Read-only and OT-safety are absolute.** Any write-back path to a control system is an automatic Critical.
5. **Evidence is mandatory.** Every band above *Needs work* carries file\:line or a reproducible run/command; "looks done" is not evidence.
6. **Induce the fault.** Where a criterion concerns failure handling (a 500, a schema change, a bad join, a concurrent edit, a tier toggle, an expired license), the reviewer **induces the condition** and observes the exact specified behavior — never reads a claim.
7. **Score the lowest persona.** The product ships when all six reviewers can sign — not on average, but each.

## C5 · The surprise-question gate (the demo must survive these live)

A skeptical buyer will ask tricky questions; the demo is not ready until each is answered **honestly, on the build**. These are scored as part of personas A3/A5 (engineer/executive) and A2 (security).

**General**
- Describe briefly what the app is and why I should buy it.
- What is the app's workflow?
- Does the first-time configurator need strong database/programming experience? *(For the common case, no — the no-code mapper + templates; safe-SQL only for the long tail.)*
- Can I later add/remove/modify a page, widget, chart, job, or AI binding, and bind a widget to a specific query result, **easily from my HMI** — or only from source code? *(From the HMI.)*
- How much data do I need before your AI gives a mature answer? *(Simple dashboards/KPIs work day one; advanced findings arrive as readiness gates turn ready; a backfill collapses the timeline.)*

**License**
- What license types exist and what **exactly** does each grant?
- How do you (the seller) control the license type? *(A signed token, not an editable row.)*
- One-time purchase or renewed monthly/yearly/for-a-duration with an expiry?
- Does each license limit the number of users or the number of DB/source connections? *(Yes — enforced by the signed seat/source caps.)*

**User / Role / Admin**
- What user types exist and each one's privileges?
- How do I add and manage them?
- What is the user-count limit?
- Where are user passwords stored and how? *(Argon2id-hashed, never plaintext.)*
- Can the same user have two concurrent sessions on two devices?
- If two users open the same page and one modifies it, what does the other see? *(An optimistic-concurrency conflict dialog, not a silent overwrite.)*
- Do you ship a customer-usable admin inside the install image? *(No — the automated install provisions only the permanent `sysadmin` support account, which SOU uses for support and the customer never sees; the customer's own admin is created manually at commissioning. So nothing customer-facing is baked into the image.)*

**AI / ML**
- Does the system work on AI or ML?
- Is all analysis AI, or simple math? *(Deterministic engines compute; the assistant only explains.)*
- Does the AI assistant do all the analysis, or only suggestions/recommendations? *(Only explanation/suggestion; engines do the math.)*
- Describe the AI engine's workflow.
- Do you own the engine, or are you linked to GPT/Claude — sending data out and getting results back? *(Engines run in-tenant; the assistant model is self-hosted by default, or a zero-retention private endpoint receiving only the question + scoped evidence.)*
- An AI engine needs heavy resources and big data — not any laptop can handle it; where does this app run? *(Defined deployment topologies/sizing; engines are deterministic, not a giant LLM doing arithmetic.)*
- GPT-3 (~175B params) erred often; GPT-4 (~1.76T) is better — how can I depend on your assistant? *(Because the assistant does not compute or rank; deterministic engines do, and every assistant claim carries a resolvable evidence handle or is not rendered.)*

# Visual Data Preparation and Transformation Builder - Design Specification

A dual-mode, no-code / low-code surface for building ETL and data-preparation
logic against linked source tables. The user either wires a visual transform
graph or writes SQL, tests the result on a sample, and saves the result as a
named, versioned transformation definition.

This spec assumes a read-only, evidence-grade platform: the builder never
mutates source data. It produces a saved definition (linked to a job), and the
generated output is a derived view or a governed materialised result, never a
write-back to the source system. This matches the dual-mode "config surface"
pattern (a surface that saves a definition linked to a job).

---

## 1. The single most important correction to the draft

The draft treats three different kinds of block as if they all sit on the same
canvas and wire to each other freely: arithmetic/logical operators
(`AND`, `OR`, `+`, `>`), relational operators (`filter`, `group by`, `sort`),
and control flow (`if/else`, `loop`). They operate at three different
granularities and must not share one wiring surface. Mixing them is the root
cause of most "what does this wire even mean" ambiguity.

Three layers, cleanly separated:

| Layer | Lives where | Nodes operate on | Wire carries |
|-------|-------------|------------------|--------------|
| Dataflow (transform graph) | The canvas | Whole datasets (relations) | A dataset: rows x typed columns |
| Expression | Inside a single node's editor | Scalars, columns, literals | Nothing on the canvas; expressions are node config |
| Orchestration | A separate pipeline surface (out of scope here) | Steps / jobs | Control tokens (success, branch, iterate) |

Consequences:

- The canvas is a Directed Acyclic Graph (DAG) of relational transforms.
  Cycles are illegal.
- `AND / OR / NOT / + / - / % / > / < / >= / <= / if-else` are not canvas
  blocks. They are the vocabulary of the Expression editor that opens inside
  a Filter node, a Derived-Column node, or a Join-condition editor.
- `loop`, `if-then` (as flow control), and scheduling belong to orchestration,
  not to a row-level transform graph. A transform graph is declarative: it
  describes what the output relation is, not an imperative sequence of steps.

Everything below follows from this.

---

## 2. Canonical artifact: what "save" actually produces

"Save as a file" is underspecified. Define the saved object precisely so it is
reproducible, portable, and auditable.

A saved **Transformation Definition** contains:

- `id` (stable UUID), `name`, `description`, `author`, `created_utc`,
  `updated_utc`, `version`, `status` (draft | published).
- `authoring_mode`: `visual` or `sql` (see section 5).
- `graph`: the node/edge model as JSON (nodes, ports, wires, expressions,
  layout). Present only in visual mode.
- `compiled_sql`: the SQL the graph compiles to (or the hand-written SQL in
  SQL mode), pinned to a target dialect.
- `target_dialect`: postgres | mysql | sqlserver (or an internal logical plan
  that transpiles, see section 14).
- `source_bindings`: references to source tables/columns by stable internal ID,
  never by display name, so a source rename does not silently break the
  definition.
- `output_schema`: inferred columns, types, nullability of the final output.
- `lineage`: per-output-column provenance back to source columns and the
  operations applied (section 11).
- `validation_snapshot`: status and any warnings at save time.
- `definition_hash`: hash over the normalised graph + bindings, for change
  detection and reproducibility.

Rules:

- A published version is immutable. Editing a published definition creates a
  new draft version; publishing supersedes the previous version but never
  overwrites it.
- Names are descriptive only. No phase, task, or version codes embedded in the
  name. Version is a separate field.
- The definition is linked to a job/owner object; it does not float free.

---

## 3. Screen layout

```
+------------------------------------------------------------------+
|  TOP BAR: [Visual | SQL] toggle   name   Validate  Preview  Save |
+-----------+--------------------------------------+---------------+
|  LEFT     |            CANVAS                     |   RIGHT       |
|  Schema   |   (node graph, pan/zoom, minimap)     |   Node        |
|  browser  |                                       |   palette     |
|           |                                       |               |
+-----------+--------------------------------------+---------------+
|  BOTTOM: Preview grid  |  Problems  |  Generated SQL  |  Lineage  |
+------------------------------------------------------------------+
```

- **Top bar**: mode toggle, definition name, Validate, Preview (sample run),
  Save / Publish, undo/redo, zoom-to-fit. In SQL mode the palette collapses
  and only the schema browser plus the SQL editor and result grid remain.
- **Left - schema browser**: linked source tables only (the platform starts
  empty; only imported/linked tables appear). Per table: qualified name, source
  connector, row-count estimate, columns with type / nullable / PK / FK,
  sample values on hover. Search and filter. Multi-select columns and drag a
  whole table or selected columns onto the canvas to create a Source node.
  FK relationships are surfaced to suggest joins.
- **Canvas**: the transform DAG. Pan, zoom, snap-to-grid, minimap,
  multi-select, copy/paste, undo/redo, node comments/annotations, node search
  (spacebar or right-click), keyboard shortcuts. Nodes are colour-coded by
  state: valid, warning, error. While dragging a wire, compatible input ports
  highlight and incompatible ones dim.
- **Right - node palette**: the transform catalogue (section 7), grouped and
  searchable. Drag onto canvas.
- **Bottom dock (tabs)**:
  - Preview: sample result grid for the currently selected node.
  - Problems: the full validation list (errors and warnings), each linking to
    the offending node/port.
  - Generated SQL: read-only view of what the graph compiles to.
  - Lineage: provenance for a selected output column.
- **Inspector** (opens on node select): the node's configuration, including its
  Expression editor where relevant.

---

## 4. The wiring correctness engine: node and port types

This is what turns "if bad wiring, I should get error" into a precise,
predictable rule instead of an afterthought.

Every node exposes typed ports. A wire is legal only if the output port type is
compatible with the input port type and the schema constraints hold.

Port types:

- **Dataset**: a relation with a known schema (ordered columns, each with a
  type and nullability). This is what flows along most wires.
- **Column reference**: a pointer to a column within a dataset (used by node
  config such as a group key, not usually a free canvas wire).
- **Scalar**: a single typed value (used inside expressions).
- **Predicate**: a boolean expression (a filter condition, a join condition).

Wire legality (checked live, at drag time):

- Dataset out -> Dataset in: legal if the consuming node accepts the upstream
  schema. Some nodes require specific columns or types; those constraints are
  checked here.
- You cannot wire a Dataset into a scalar input, or a Scalar into a Dataset
  input. This is the type error that stops the nonsense wiring the draft was
  worried about.
- Multi-input nodes declare arity: Filter has 1 dataset input; Join has 2;
  Union has 2 or more; a Source has 0 inputs; a Sink has 1 input and 0 outputs.

Structural rules enforced continuously:

- No cycles. Adding a wire that would create a cycle is rejected at drag time
  with a clear reason.
- Every node's required inputs must be connected before it is considered valid.
- At least one Sink/Output node is required before a definition can be saved as
  runnable (draft can be saved incomplete, published cannot).
- Orphan nodes (not reaching any sink) are a warning, not an error.

---

## 5. Dual mode: Visual and SQL, and the honest toggle contract

The draft implies free two-way toggling. Naive round-tripping between a visual
graph and arbitrary SQL is lossy and a reliability trap. Define the contract
explicitly.

- **Visual -> SQL is always available and deterministic.** The graph compiles
  to SQL for the target dialect. Users can view the generated SQL read-only at
  any time.
- **SQL mode is a first-class authoring mode**, not a transient view. In SQL
  mode the user writes SQL directly; it is validated by parse + schema
  inference + a sampled dry run, and produces the same artifact type (a saved
  definition).
- **Switching a visual definition to SQL mode forks it.** The generated SQL is
  handed to the SQL editor; the graph detaches and becomes read-only history.
  The user is warned this direction is one-way.
- **SQL -> visual reconstruction is best-effort and limited.** Offer it only
  for the SQL subset the parser can faithfully map to nodes (simple
  select/filter/join/group/sort). For anything outside that subset (window
  functions, vendor-specific syntax, correlated subqueries, CTEs) the tool
  keeps the definition in SQL mode rather than producing a wrong or partial
  graph. Do not pretend a full round trip exists.

State the target SQL dialect explicitly on the definition. If the platform has
multiple connector engines, compile to an internal logical plan first and
transpile per dialect (section 14), so one definition can target Postgres,
MySQL, or SQL Server without hand-editing.

---

## 6. SQL-mode workflow

- Left schema browser stays available; clicking a table or column inserts a
  qualified reference at the cursor.
- Editor features: syntax highlighting, schema-aware autocomplete
  (tables/columns/functions), identifier quoting per dialect, format/prettify.
- **Test** runs the query in read-only mode on a capped sample and shows the
  result grid plus the inferred result schema below. Row cap and statement
  timeout are enforced; the query is wrapped or rewritten to guarantee a LIMIT
  and to reject any statement that is not a single read (no INSERT, UPDATE,
  DELETE, DDL, or multi-statement batches).
- On error, show the engine error with line/column, the offending token, and a
  plain-language hint where the class of error is recognised (unknown column,
  ambiguous column, type mismatch, missing group key).
- Save produces the same versioned definition, with `authoring_mode = sql`.

---

## 7. Node catalogue (replacing the draft's four groups)

Grouped by what they do to a relation. This is the right-hand palette.

**Sources**
- Source Table: bind to a linked table (created by dragging from the schema
  browser). 0 inputs.
- Reference to another saved definition: compose pipelines by consuming a
  previously saved transformation's output (with cycle protection across
  definitions).

**Row-level transforms** (1 dataset in, 1 out; do not change row count)
- Derived Column / Compute: add or replace a column from an Expression.
- Rename Column.
- Cast / Convert Type (with explicit handling of lossy casts, section 13).
- Replace Nulls / Coalesce.
- String ops: split, extract, trim, case-fold, pad, concat (via Expression).
- Conditional value: `if / else` at the value level (a CASE expression), which
  is where the draft's "if else" actually belongs.

**Filtering and sampling** (may reduce row count)
- Filter: keep rows where a Predicate is true. Note the NULL semantics in
  section 8.
- Distinct / Deduplicate (with an optional key set).
- Limit / Top N / Sample.

**Aggregation**
- Group By: one or more group keys plus aggregate expressions
  (count, sum, avg, min, max, count distinct, first/last with explicit order).
  Selecting a non-aggregated, non-key column is an error, surfaced at edit time.

**Relational / set** (2+ inputs)
- Join: inner / left / right / full, with an explicit key mapping and join
  Predicate. Warns on fan-out risk and on accidental cross join when no key is
  given.
- Union / Union All: requires column-compatible inputs; provides a column
  mapping UI when names or order differ.
- Except / Intersect.

**Reshape**
- Pivot / Unpivot.
- Window functions: partition by, order by, frame; running totals, rank,
  lag/lead. (Available in visual mode as an explicit node; this is one of the
  constructs that will not round-trip cleanly from SQL.)

**Ordering**
- Sort: one or more keys with direction and null-ordering. Note: sort order is
  only guaranteed at a Sink or an explicit Limit/Top-N boundary; intermediate
  ordering is not guaranteed to survive later operators (section 13).

**Sinks / Outputs**
- Output: names the final relation, defines the output schema, and is the
  target of Save. At least one is required to publish.

The draft's "flowchart: if/else, then, loop" group is removed from this surface.
Value-level `if/else` becomes the Conditional value node; pipeline-level
branching and loops belong to the orchestration surface.

---

## 8. Expression editor and NULL semantics

Opened from inside Filter, Derived Column, Join condition, and aggregate
definitions. This is the home of the arithmetic and logical operators from the
draft. Offer both a small visual sub-builder and a text formula box backed by
the same grammar and validated identically.

Operators: `+ - * / % ( )`, comparison `= <> > < >= <=`, logical
`AND OR NOT`, `IN`, `BETWEEN`, `LIKE`, `IS NULL`, `CASE WHEN ... THEN ...
ELSE ... END`, plus a curated function library (string, numeric, date/time,
cast).

Static checks in the editor: referenced column exists in the input schema,
operand types are compatible, functions get the right argument types, and the
result type is inferred and shown.

NULL and three-valued logic must be explicit, because it is the most common
source of "the filter dropped rows I expected to keep":

| A | B | A AND B | A OR B | NOT A |
|---|---|---------|--------|-------|
| T | T | T | T | F |
| T | F | F | T | F |
| T | NULL | NULL | T | F |
| F | NULL | F | NULL | T |
| NULL | NULL | NULL | NULL | NULL |

A Filter keeps a row only when the predicate is TRUE. NULL (unknown) is not
kept. Surface this in the UI (for example, an explicit "treat NULL as ..."
choice on comparisons, and an `IS NULL` helper) so users do not silently lose
rows.

---

## 9. Validation model and error taxonomy

Three levels, always distinguishable:

1. **Continuous static validation** while editing (no execution): wiring
   legality, schema inference, expression checks. Results stream into the
   Problems panel and colour the nodes.
2. **Validate** (explicit, still no execution): full graph compile to SQL,
   confirming the definition is structurally and semantically sound end to end.
3. **Preview** (sampled execution, section 10): proves it actually runs against
   real data.

Distinguish hard errors (block save/publish) from warnings (allowed, flagged).

Hard errors:
- Structural: cycle, missing required input, no sink, disconnected required
  port.
- Type: dataset wired to scalar port, incompatible union schemas, wrong operand
  types in an expression.
- Schema: unknown column, ambiguous column after a join, group-by selecting a
  bare non-key column, aggregate used outside an aggregation context.

Warnings:
- Cross join with no key (possible but usually a mistake).
- Fan-out join that multiplies rows.
- Lossy implicit cast (for example numeric to text, wide to narrow).
- Float equality comparison.
- Orphan node not reaching any sink.
- Sort followed by an operator that does not preserve order.

Every problem entry names the node/port, states the rule, and offers a "reveal"
action. Errors block publish; drafts may be saved with warnings, and with
errors only as an explicit "save incomplete draft".

---

## 10. Preview and test execution

- Read-only always. The preview path can only issue read queries; it is
  physically prevented from writing (section 15).
- Sample-based: cap rows (for example the first or a sampled N), enforce a
  statement timeout, and never pull an unbounded result into the client.
- Per-node preview: selecting any node shows the sample output at that node, not
  just the final one. This is the biggest debugging aid and is missing from the
  draft.
- Show the inferred schema alongside the sample so type surprises are visible
  before a full run.
- Preview reflects the compiled SQL, so what the user tests is what the saved
  definition will run. Note clearly that a sample can hide data-dependent issues
  (a cast that fails only on a row not in the sample); full validation on the
  real run still applies.

---

## 11. Lineage and evidence-grade provenance

For an evidence-grade platform this is not optional and is a genuine
differentiator.

- Every output column records its provenance: which source column(s) it derives
  from and the ordered operations applied (filter, cast, aggregate, join key,
  expression).
- Lineage is computed at compile time and stored on the definition, and it is
  browsable in the Lineage tab: click an output column, see the graph path back
  to source columns.
- Reproducibility: pin the source snapshot/version used for a published run so
  the same definition over the same source snapshot yields the same output. The
  `definition_hash` plus source snapshot id together identify a reproducible
  result.

---

## 12. Governance and access

- Read-only guarantee enforced at the execution layer, not just by convention.
- Permissions: who can create drafts, who can publish, who can run. A saved
  definition inherits ownership and is subject to the platform's access control
  (deny-by-default; every new endpoint/action explicitly granted).
- Audit: creation, edits, publish, and runs are logged with author and time.

---

## 13. Bug and edge-case register (anticipated failure modes)

Grouped so each has an owner during build. These are the things that break
data-prep tools in production.

**NULL and logic**
- Three-valued logic dropping rows unexpectedly (section 8). Make NULL handling
  explicit on comparisons and filters.
- Aggregates ignoring NULLs (for example AVG over NULLs) versus counting them;
  make count vs count-distinct vs count(*) explicit.

**Numeric**
- Division by zero: guard with a nullif/zero-safe option; define the result
  (error vs NULL) and surface the choice.
- Integer vs floating division and truncation.
- Overflow on sum/product over large columns; choose a wide accumulator type.
- Floating-point equality: warn and suggest tolerance-based comparison.

**Types and casts**
- Lossy or failing casts (text to number on dirty data). Offer safe-cast
  (invalid -> NULL) vs strict-cast (row/run error), and make the choice visible.
- Implicit coercions differing by dialect.

**Date, time, locale, encoding** (a class this platform has already been bitten
by)
- Timezone handling: store and compare in a defined zone; do not compare a
  timestamp with and without timezone.
- Locale-sensitive date parsing (day/month order) on differently configured
  machines. Parse with explicit formats, never machine locale.
- Text encoding: render preview as UTF-8; guard against mojibake from
  code-page round-trips.

**Relational**
- Column name collisions after a join; require aliasing/prefixing and flag
  ambiguity as a hard error.
- Identifier case-folding differences across dialects (unquoted identifiers
  folded to lower vs upper); quote consistently in generated SQL.
- Join fan-out silently multiplying rows; warn and show row-count deltas in
  preview.
- Accidental cross join when a key is omitted; warn.
- Union of schemas that differ in column count/order/type; require an explicit
  mapping.

**Ordering and determinism**
- No guaranteed order without an explicit sort at the sink; a mid-graph sort may
  not survive downstream operators. Warn.
- Non-deterministic first/last in aggregation without an explicit order key.

**Data shape and scale**
- Empty input dataset: define behaviour (valid, produces empty output, not an
  error).
- All-NULL or single-value columns.
- Very wide tables (hundreds of columns): virtualise the schema browser and
  preview grid; do not render everything.
- Large previews: hard row cap and pagination; never stream a full table to the
  client.

**Definition lifecycle**
- Schema drift: source table changed columns/types since the definition was
  saved. Re-validate on load and before run; block with a clear diff rather than
  failing mid-run.
- Broken source binding after a rename: bindings are by stable id, so a rename
  does not break silently; a delete is caught at validation.
- Circular reference across composed definitions (definition A consumes B
  consumes A): detect at save.
- Expression referencing a column produced later in the same node or not yet
  computed: reject with a clear message.

**Authoring / editor**
- Autosave versus concurrent edit conflicts: last-writer-wins is unsafe; use
  optimistic version checks and warn on conflict.
- Undo/redo across destructive ops (node delete, wire delete) must restore
  wires and config, not just node position.
- Copy/paste of a node must not duplicate a stable id in a way that corrupts
  lineage.

**Security (SQL generation and execution)**
- Identifier and literal handling in generated SQL: quote identifiers, avoid
  string-concatenating user values into SQL; parameterise. Prevents injection
  and quoting bugs in one move.
- Enforce single-read-statement only on any executed SQL (preview and run);
  reject DDL/DML and multi-statement batches by parse, not by string search.
- Timeouts and row/cost caps on every execution path.

---

## 14. Non-functional

- **Dialect strategy**: compile the graph to an internal logical plan, then
  transpile per target dialect (Postgres, MySQL, SQL Server). One definition,
  multiple engines, without hand edits. SQL-mode definitions are pinned to a
  single dialect.
- **Performance**: static validation and schema inference run incrementally on
  edit, not as a full recompute each keystroke. Preview is sampled and capped.
- **Internationalisation**: UTF-8 throughout; explicit date/number formats;
  no reliance on machine locale.
- **Portability**: the definition JSON plus compiled SQL is exportable and
  re-importable; `definition_hash` detects drift.
- **Accessibility**: keyboard-navigable canvas and palette; colour is not the
  only signal of node state (icons/text too).

---

## 15. Read-only enforcement (execution layer)

Do not rely on the UI to keep the tool read-only. Enforce it where queries run:

- Execute preview and run under a role/connection with read-only privileges on
  source.
- Parse every statement and reject anything that is not a single SELECT.
- Wrap or rewrite to guarantee a LIMIT on preview; enforce timeout and max rows.
- Outputs go only to the platform's own governed store (a view or a materialised
  result linked to the job), never back to the source.

---

## 16. Suggested build order (MVP first)

1. Schema browser + Source node + Output node + wire type system + static
   validation + generated-SQL view. (Proves the core model and the error
   engine.)
2. Filter, Derived Column, Sort, Limit + Expression editor with NULL semantics
   + per-node sampled preview.
3. Group By and Join (with fan-out and collision handling) + lineage capture.
4. Save/version/publish + read-only execution enforcement + governance.
5. SQL mode (authoring + test + save) and the one-way visual-to-SQL fork.
6. Reshape/window nodes, multi-dialect transpile, composed-definition
   references.

Ship each phase as something that runs end to end rather than half-building
every node at once.

	# Analytics Dashboard and Widget Layer - Build Checklist

Modeled on Qlik Sense patterns, adapted for a read-only, evidence-grade,
process-to-quality platform. Tick items as you build. Items marked CORE are the
minimum for a credible demo; items marked PPIQ are domain-specific and matter
more here than in generic BI; items marked LATER are enhancements.

The dashboard/widget builder is itself a config surface: it saves a named,
versioned dashboard definition (sheets + widgets + bindings), consistent with
the transformation-definition artifact.

## 0. Associative / selection engine (this is what makes it "like Qlik")

The chart list is the easy part. The associative model is the differentiator.
Build this first or the rest is just static charts.

- [ ] CORE Selection state per value: selected, possible (associated), excluded,
      alternative (Qlik green / white / gray / light-gray semantics)
- [ ] CORE Click any data point to select; the selection filters every widget
      on the page (cross-filtering / linked views)
- [ ] CORE Global selections bar showing all active selections as removable chips
- [ ] CORE Clear-all, clear-one, and clear-others actions
- [ ] CORE Selection history: step back / step forward
- [ ] CORE "Possible vs excluded" visually distinct inside filter panes and
      list boxes (so the user sees what is still reachable)
- [ ] Lock / unlock a selection so it survives clear-all
- [ ] Global smart search across dimensions (type a value, see where it exists)
- [ ] Alternate states (two independent selection sets for side-by-side compare)
- [ ] Selection applied as chip AND reflected in the URL / shareable state
- [ ] Debounced recompute so rapid clicks do not fire a query per click

## 7. UI/UX standards (behavior, not looks)

- [ ] CORE Consistent interaction grammar: click = select, hover = tooltip,
      lasso/drag = range select - identical across all charts
- [ ] CORE Tooltip on hover with dimension, measure, and formatted value
- [ ] CORE Loading skeletons, not spinners, per widget
- [ ] CORE Empty state ("no data") distinct from filtered-to-empty state
      ("no rows match current selection - here is what to relax")
- [ ] CORE Error state per widget (query failed) without breaking the page
- [ ] CORE Drill down (within a dimension hierarchy) and drill through (to a
      detail sheet), with a visible affordance
- [ ] Cross-filter feedback: clicking here visibly updates there
- [ ] Undo/redo of selections reachable by keyboard
- [ ] Keyboard navigation and focus order across widgets
- [ ] Accessibility: ARIA roles, screen-reader labels, min contrast, focus
      rings, do-not-rely-on-color-alone
- [ ] Responsive reflow tested on tablet and phone widths
- [ ] Latency budget: first paint fast, progressive data fill, virtualized
      tables for large results
- [ ] Sensible defaults: sort, top-N cap, label overlap avoidance, axis start
      at zero where honest
- [ ] Confirm-before-destructive on layout edits (delete widget, delete sheet)
- [ ] Autosave with version/conflict handling in the builder

## 9. Evidence-grade and read-only requirements (PPIQ)

These separate this from a generic BI clone and should be non-negotiable.

- [ ] PPIQ Every widget traces to its underlying query/definition (lineage view:
      "what data and transforms produced this number")
- [ ] PPIQ Drill-to-evidence: from a KPI or bar down to the source rows/units
      behind it
- [ ] PPIQ Sample-data disclosure badge when a widget renders emulated/sample
      data rather than real imported data
- [ ] PPIQ "As-of" timestamp and source snapshot id on every sheet/widget for
      reproducibility
- [ ] PPIQ Read-only enforced at the query layer; dashboards can never write back
- [ ] PPIQ No hardcoded/demo content in any widget (Generic Only; Starts Empty -
      an unconfigured app shows empty states, not fake charts)

## 12. Suggested MVP cut (build order)

1. Associative engine + global selections bar + one filter pane + cross-filter.
2. CORE charts: bar, line, KPI, straight table + master items + Dark-Industrial
   theme + tooltip/empty/loading/error states.
3. Sheets + responsive grid + save dashboard definition + export.
4. Drill-down, conditional formatting, reference/target lines.
5. PPIQ pack: genealogy graph, SPC/capability charts, drill-to-evidence,
   sample-data badge, lineage view.
6. Bookmarks, storytelling, alerts, Insight/correlation auto-suggest, maps.

Ship each layer working end to end before widening the chart list.
