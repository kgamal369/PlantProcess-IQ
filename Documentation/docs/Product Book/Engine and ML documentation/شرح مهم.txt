# 1. CHALLENGE THE CURRENT RESOURCE ARCHITECTURE

The current Chapter-4 and Pack contract says:

`ml parallelism = 1`

while admission is:

`sum(running compute_weight) + candidate_weight <= parallelism`

and model training may carry:

`compute_weight = 4`.

That is internally inconsistent: a weight-4 candidate cannot be admitted into capacity 1.

More importantly, the same `ml` lane currently carries both:

* long-running training / encoder / index / SHAP work;
* operational event and micro-batch scoring.

That can allow training work to delay a prediction whose usefulness depends on an actionable deadline.

Do not preserve this merely because it exists in Chapter 4.

Design a better model.

Preferred direction to evaluate:

Logical job class may remain `ml`, but separate physical workload/resource lanes:

* training;
* batch scoring;
* operational / online scoring.

Operational scoring must have reserved serving resources, warm models and a latency budget independent of training occupancy.

Training must be checkpointable, low-priority and pre-emptible where the runtime supports it.

Separate:

`max_concurrency`

from:

`resource_capacity / compute_weight`.

Do not use one number to mean both concurrency and resource cost.

Reconcile Chapter 4, Chapter 6 and the Layer-B Pack around the chosen design.

---

# 2. SEMANTIC VERSIONING — TAKE THE BEST OF BOTH DESIGNS

Your `SemanticModelVersion` solves a genuine reproducibility problem, but it currently behaves like an additional lifecycle authority.

The Chapters already own version authority through:

* definition_versions;
* relationship source_definition_id/version;
* feature-set versions;
* snapshot identities;
* model registry versions.

Design a hybrid:

**Semantic Contract Manifest / Semantic Publication Manifest**

It should be an immutable, content-addressed reproducibility pin over the canonical versions in force.

It may contain:

* manifest id;
* content hash;
* exact definition-version references;
* relationship publication id/version;
* relevant registry/configuration versions;
* creation/publication timestamp.

It must NOT create a competing draft/validated/published/rolled-back lifecycle.

Think of it as a Git commit over the semantic contract, not a fourth authoring authority.

If this is judged superior, update Chapters 2/3/4 as well as the Pack.

---

# 3. FEATURE DATA PATH — OPTIMISE FOR BOTH GOVERNANCE AND TRAINING

Retain:

`ppiq_plant.feature_store`
with incremental refresh and canonical lineage.

But state explicitly:

**PostgreSQL JSONB is not the hot training tensor path.**

The training contract should be:

live governed feature state
-> seal immutable snapshot
-> typed columnar snapshot
-> Python data loader.

Evaluate Parquet / Arrow or an equivalent replaceable columnar snapshot format.

Training must not repeatedly deserialize millions of JSONB feature objects from PostgreSQL.

PostgreSQL owns governance and current state.

The immutable columnar snapshot owns high-throughput training input.

---

# 4. SEQUENCE STORE — REDESIGN THE PHYSICAL PAYLOAD

The current sequence product is potentially the largest data product.

Do not default to storing massive numeric sequence payloads as PostgreSQL arrays.

Evaluate a split contract:

PostgreSQL:

* manifest;
* subject/grain identity;
* channel-set version;
* time range;
* sample count;
* completeness;
* content hash;
* storage URI;
* snapshot identity.

Object/artifact storage:

* immutable chunked typed numeric sequences;
* compressed;
* partitioned;
* streamable / memory-mappable where appropriate.

The PyTorch loader should consume bounded chunks rather than giant database rows.

Keep the logical sequence contract generic.

Choose physical layout by measured read throughput and storage amplification.

---

# 5. MODEL SELECTION MUST OPTIMISE QUALITY AND SERVING COST TOGETHER

Keep:

* simple baseline first;
* LightGBM as an initial tabular candidate;
* TCN / 1D CNN versus Transformer measured;
* encoder optional;
* SHAP as predictive contribution, never causality.

Strengthen promotion.

A model must not win on AUC / accuracy alone.

Champion/challenger evaluation must include:

QUALITY

* discrimination/error;
* calibration;
* out-of-time performance;
* subgroup/regime stability;
* missingness robustness;
* explanation stability.

SERVING

* p50/p95/p99 inference latency;
* throughput;
* artifact size;
* RAM / VRAM;
* warm-up time.

TRAINING

* training duration;
* peak memory;
* snapshot-read throughput.

A complex encoder is promoted only when measured downstream lift is worth its operational cost.

If engineered features perform as well, do not deploy the encoder merely because deep learning is available.

---

# 6. VECTOR SEARCH MUST BE POLICY-DRIVEN

Keep `VectorSimilarityIndex` as the product abstraction.

Do not standardise on one FAISS index family.

Define a benchmark selector using:

* population size;
* vector dimension;
* RAM;
* required recall@k;
* p95 latency;
* index-build time;
* update pattern.

Always retain exact Flat search on a representative sample as the correctness/recall baseline.

Allow HNSW / IVF / PQ / quantised or GPU-backed variants only when measured appropriate.

FAISS remains an implementation, not the architecture contract.

---

# 7. REDESIGN THE UNSTRUCTURED-MODALITY BOUNDARY

The current absolute rule:

`no statistic, score or value is ever computed from text`

is correct for free-form Assistant/RAG evidence but is too broad as a permanent industrial-ML architecture boundary.

Separate two paths.

## Evidence modality

Operator notes / maintenance documents used by retrieval and the LLM:

* citation/evidence only;
* may not manufacture plant facts;
* may not create an operational score directly.

## Governed multimodal ML — future capability, NOT current implementation

If future customer value justifies it:

text/image
-> explicitly authored model definition
-> versioned immutable training snapshot
-> leakage controls
-> held-out validation
-> model registry
-> calibration / drift
-> learned output with explicit claim class and provenance.

No free-form LLM output becomes a model feature.

This pass should reserve the correct architecture without adding implementation scope now.

Reconcile the image-model contract as well: an inspection-image model cannot simultaneously be registered as a vision model and be prohibited from producing any learned result.

---

# 8. LLM / ASSISTANT IS CORE — GIVE IT ITS OWN IMPLEMENTATION-GRADE ARCHITECTURE

The Layer-B Pack currently delegates broader Assistant architecture to DF15.

That separation is fine organisationally, but PPIQ cannot call the complete AI architecture frozen without an equally deep Assistant / LLM runtime design.

Produce or update a dedicated Assistant / LLM Architecture section/pack covering:

user
-> permission/tenant context
-> deterministic tool planner
-> structured Layer A / Layer B tools
-> permission-scoped evidence retrieval
-> evidence packing / context budgeting
-> model gateway
-> LLM
-> answer verification
-> cited response.

Preserve these hard rules:

* the LLM does not calculate plant facts;
* the LLM does not replace an engine refusal;
* every numeric claim resolves to evidence;
* claim classes cannot be upgraded by language;
* external providers receive minimum scoped evidence only;
* self-hosted, private-provider and BYOM modes remain available;
* model/provider change is a governed release event.

Design hybrid retrieval explicitly:

* structured tools first for facts and analytical results;
* full-text + embeddings for documents/evidence where appropriate;
* optional re-ranking if benchmarks justify it;
* permission filtering before context reaches the LLM;
* deduplication and token-budgeted evidence packing.

Define Assistant quality gates:

* tool-selection accuracy;
* groundedness;
* citation correctness;
* unsupported-claim rate;
* refusal correctness;
* causal-overreach rate;
* multilingual fidelity;
* time-to-first-token;
* total p95 answer latency;
* serving throughput;
* memory/VRAM.

For self-hosted serving, use a replaceable `ModelServingRuntime` abstraction.

vLLM or equivalent may be benchmarked as an implementation; no serving library becomes the product contract.
